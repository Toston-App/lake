## Architecture (what the plans build)

```
 Claude.ai / Claude Code ─┐
 ChatGPT (dev-mode conn.) ─┤   HTTPS  POST /mcp   (MCP Streamable HTTP, stateless)
 Grok connectors / xAI API ┼──────────────────────────────┐
 OpenCode / Cursor / Codex ┘   Authorization: Bearer <tok>│
                                                          ▼
                     ┌────────────── existing FastAPI backend ─────────────┐
                     │ /.well-known/oauth-protected-resource  (plan 002)   │
                     │ /mcp  ── BearerAuth ASGI middleware (002, 004)      │
                     │        └─ mcp low-level Server  (002)               │
                     │             └─ app/mcp_server/tools.py  (001)       │
                     │                  ├─ ai/chat_tools.execute_tool  ◄── already used by in-app chat
                     │                  └─ two-step confirm (Redis)    ◄── reuses chat pending actions
                     └──────────────────────────────────────────────────────┘
        OAuth authorization server = Clerk (users already sign in with Clerk)

 integrations/toston/  (plan 003): SKILL.md + Claude plugin + per-client install docs
```

Key facts from recon that shape this:

- The in-app chat already has a **typed, ownership-checked tool layer**:
  `backend/app/app/ai/chat_tools.py:756` `execute_tool(tool_name, args, db, user)`
  dispatches to the domain services, validates args against
  `TOOL_ARG_MODELS` (`backend/app/app/ai/tools.py:482`), and has a confirmation
  policy (`requires_confirmation`, `chat_tools.py:73`). The MCP server is a thin
  adapter over this, so no business logic is duplicated.
- With MCP, **the user's LLM pays for inference**. Toston's OpenRouter costs and
  the `monthly_token_limit` quota (`core/tiers.py`) don't apply. Only DB and
  Redis load remain, so the MCP path is rate-limited, not token-metered.
- Users authenticate with **Clerk** (`api/deps.py:76`). Clerk can act as an
  OAuth 2.1 authorization server for MCP (Dynamic Client Registration and
  Client ID Metadata Documents), so no login system needs to be built.
- The backend runs with 4 worker processes
  (`backend/backend.dockerfile:43`: `fastapi run --workers 4`), so the MCP
  transport must be **stateless**: any request can land on any worker.

## Findings considered and rejected

- **Reusing the pydantic-ai `FunctionToolset` from `ai/agent.py` as the MCP surface**: rejected. Those tool functions return Vercel AI `DataChunk` UI metadata and depend on `ChatDeps.conversation_id` and turn telemetry. `execute_tool` is the clean, UI-free entry point.
- **Using `FastMCP` decorator-style tools**: rejected for this codebase. The arg models already exist as pydantic classes, so the low-level `Server` with `list_tools`/`call_tool` handlers uses them directly. With FastMCP each tool would need a hand-written signature (or a nested `payload` arg).
- **Token-quota metering on MCP calls**: rejected. No Toston LLM tokens are spent on this path. Rate limits cover abuse.
- **Session-ful (SSE) MCP transport**: rejected. The app runs 4 workers, so stateless Streamable HTTP avoids sticky sessions.
